# ホームページ修正の運用ルール

状態: 承認済み（2026-11-17）
作成日: 2026-11-17
対象サイト: https://www.inabu-jaburo.jp/

本書は、ホームページの変更を修正単位で記録し、変更前の状態へ戻せるようにするための運用ルールです。2026-11-17にユーザーレビュー・承認を受けて運用を開始しました。個々のサイト修正はユーザーの依頼・承認範囲に従います。

## 保存場所と修正単位

修正情報とバックアップは、本書と同じ階層の `HP修正/` に保存します。

一つの目的に対応する変更を一つの修正単位とし、修正単位ごとに `YYYYMMDD_NN_修正名/` フォルダを作成します。日付は日本時間の着手日、NNは同日の連番（01から）です。関連する複数ファイルの変更は同じフォルダにまとめ、目的が異なる変更は分けます。記録済みのフォルダ名は原則変更しません。

```text
issue-000-HP運営/
├── README.md
├── OPERATION.md
├── articles/
└── HP修正/
    └── YYYYMMDD_NN_修正名/
        ├── README.md       # 目的・対象・実施内容・確認結果・戻し方
        ├── before/         # 変更前の原本・設定記録
        ├── after/          # 適用したコード・設定記録
        ├── changes.patch   # テキストの差分（該当する場合）
        └── evidence/       # 画面や公開確認の証跡（必要な場合）
```

必要なフォルダ・ファイルだけを作成します。原稿の新規作成・通常の記事投稿は `articles/` で管理し、テーマや表示設定等の変更は `HP修正/` で管理します。

## 変更前に行うこと

1. ユーザーの依頼と承認範囲を確認し、修正単位のREADMEに目的・対象・予定操作・影響範囲を記載します。レビュー指定がある場合は承認まで適用しません。
2. 本番で実際に使用されているテーマ、対象ファイル、設定値を確認します。ローカルの古いコピーを本番の原本とみなしません。
3. 対象ファイルの変更前の全内容を `before/` に保存します。テーマ内の相対パスを維持し、取得日時・取得元・取得方法をREADMEに記録します。エディターの行番号付き表示や省略された表示だけを完全なバックアップとは扱いません。
4. WordPressの追加CSS・メニュー等、ファイルではない設定も、変更前の値を記録します。画面写真は補助資料とし、復元に必要な設定値を文章やテキストで残します。
5. 変更前の表示・動作を確認し、戻し方をREADMEに記載します。復元に必要な原本・設定値を取得できない場合は、適用せず取得方法を検討します。

## 変更の適用

- 依頼された範囲の必要最小限の変更に限定し、無関係な整形・リファクタリング・設定変更を含めません。
- 後から復活させる依頼では、元のコードを保持し、コメントの解除など具体的な復活方法を記録します。コメント化だけでバックアップを代用しません。
- 適用するコード・設定値を `after/` に保存し、テキスト変更は変更前との差分を残します。
- 編集中にユーザーや別の作業による更新が分かった場合は、現在の内容を再確認してから差分を作り直します。取得済みの古い内容で上書きしません。
- コードの変更に応じた構文確認・回帰確認を行います。表示設定のみの変更では、実際の表示確認を中心とし、形式的なテストは追加しません。

## 確認と完了記録

- 管理画面の保存成功と、公開ページへの反映をそれぞれ確認します。保存できただけで表示・動作の確認完了とはしません。
- 変更に関係するページ・リンク・一覧・絞り込み等を確認し、影響範囲に応じてPC・スマートフォン表示も確認します。
- キャッシュが影響する場合は、対象と操作を記録して再確認します。
- READMEに実施日時、実際の変更内容、確認方法・結果、未確認事項、公開URL、復元手順を記録します。確認済み・未確認・失敗を区別します。
- 復元手順には、戻すファイルや設定値、戻す操作、キャッシュへの対応、復元後の確認方法を記載します。バックアップの存在だけを根拠に「復元検証済み」とは記載しません。
- 不具合が発生した場合は影響の拡大を止め、この修正で変更した箇所を変更前へ戻して確認します。他の更新と競合している場合は原本全体を無条件に上書きしません。

## 切り戻し

切り戻しとは、今回の修正を取り消し、変更直前の表示・動作へ戻すことです。修正単位ごとに、適用前に切り戻し可能な状態を整えます。

### 適用前に決めること

- 切り戻し対象のファイル・設定値と、その変更前バックアップの場所。
- 切り戻しの判断基準。例: ページが表示できない、PHPエラーが発生する、本文や既存リンクが欠落する、対象外のページが崩れる、予定した動作を確認できない。
- 復元する順序・操作方法・必要な権限と、復元後の確認項目。複数ファイルや設定が相互に依存する場合は、整合性を保てる順序を記載します。
- 切り戻しによって失われる可能性がある変更やデータ。DB・記事データを変更する場合は、ファイルのバックアップだけでは戻せないことを明記し、対象に応じた退避・復元方法を準備します。

### 実施手順

1. 判断基準に該当したら追加の変更を止め、発生した症状・時刻・対象を記録します。今回の修正で発生した不具合への切り戻しは、承認された修正範囲の復旧として実施します。
2. 本番の現在の状態と変更後の内容を照合します。他の作業による更新がないか確認し、必要に応じて切り戻し直前の状態も退避します。
3. `before/` の原本・設定記録を基に、今回変更した箇所を戻します。別の更新が混在している場合は、それを巻き戻さないよう差分で戻します。範囲の分離ができない、バックアップが不完全、記事等の新しいデータを失うおそれがある場合は、無条件に復元せずユーザーへ状況を報告して対応を確認します。
4. 保存・反映を確認し、必要な場合は対象のキャッシュを削除します。ファイルや設定の復元と、キャッシュ上の表示を区別して確認します。
5. 変更前と同じ確認項目で公開ページ・関連機能を確認します。管理画面の保存成功だけでは切り戻し完了としません。
6. READMEに切り戻し理由、開始・終了日時、戻した対象、使用したバックアップ、実施操作、確認結果、残る問題を記録し、ユーザーへ報告します。変更後のコード・差分・証跡も削除せず残します。

### 記録と完了条件

- 状態は `切り戻し中`、確認できた場合は `切り戻し済み` とします。復元操作をしても確認が終わっていない場合は、その旨と未確認項目を残します。
- 切り戻し手順の記載、事前の復元検証、実際の切り戻し実施は、それぞれ区別して記録します。
- Gitのコミットを戻すだけでは本番は復旧しません。本番ファイル・設定への反映と公開確認まで行います。無関係なコミットの取り消しや履歴の強制書き換えはしません。
- 切り戻し後に再修正する場合も、直前の本番状態を確認し、再適用の差分と結果を追記します。既存のバックアップ・記録は上書きしません。

## 修正単位READMEの記載項目

- 状態: 計画中 / レビュー待ち / 作業中 / 確認済み / 一部未確認 / 切り戻し中 / 切り戻し済み
- 依頼内容・承認範囲
- 目的・対象サイト・対象ファイルや設定・影響範囲
- 変更前の状態、バックアップの取得日時・取得元・取得方法
- 予定操作と実施内容、変更前後の差分
- 確認方法・結果・未確認事項・証跡の場所
- 切り戻しの判断基準・対象・手順・復元後の確認方法
- 切り戻し実施時の理由・日時・操作・結果（実施した場合）
- コミット情報（コミットした場合）

## Git管理と秘密情報

- バックアップ・修正記録・差分はこのリポジトリで管理します。コミット・pushはユーザーの指示に従い、無関係な変更を含めません。
- このリポジトリは公開されているため、パスワード、APIキー、認証Cookie、秘密鍵、DB接続情報、個人情報を含むDBダンプ等を保存・コミットしません。
- 秘密情報を含む対象は原本を公開リポジトリに置かず、適切な非公開の保存先をユーザーと確認します。修正記録には秘密値を記載しません。
- 本ルール作成前の変更について、実際に取得していない変更前バックアップを後から作ったことにしません。後日記録する場合は、事後記録であることと復元上の制約を明記します。
